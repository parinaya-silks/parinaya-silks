## Exact webhook configuration

Use this URL, without a query string:

`https://www.parinayasarees.com/api/payments/webhook`

In Razorpay Dashboard select **Test Mode**, then **Accounts & Settings → Website
and app settings → Webhooks → + Add New Webhook**. Enter the URL, a separate
cryptographically random secret, an owner-monitored alert email and these events:

- `payment.authorized`
- `payment.captured`
- `payment.failed`
- `order.paid`
- `refund.created`
- `refund.processed`
- `refund.failed`

The webhook secret is selected/generated by the owner, not the API Key Secret.
Generate it privately using a password manager (32 or more random characters,
maximum 512). Save the identical value as `RAZORPAY_WEBHOOK_SECRET` in Vercel.
No quotes, surrounding whitespace or line breaks. This implementation requires a
secret even though the Dashboard describes it as optional. Enable the webhook
after the configured deployment is ready. Do not use the webhook URL as a browser
checkout callback URL or add a Firebase token to it.

Official references:
[Dashboard setup](https://razorpay.com/docs/webhooks/setup-edit-payments),
[raw-body validation and retries](https://razorpay.com/docs/webhooks/validate-test).

After saving server variables, **redeploy Production** so the function receives

## Required recovery worker

Configure a reliable external scheduler with this exact request every minute:

- Method: `POST`
- URL: `https://www.parinayasarees.com/api/payments/worker`
- Header: `Authorization: Bearer <PAYMENT_WORKER_SECRET>`
- Header: `Content-Type: application/json`
- Body: `{}`

Store the authorization value in the scheduler's protected configuration. Do not
put it in the URL, logs, job name or source. Allow enough request time for the
worker's 35-second work budget (the function limit is 60 seconds). A scheduler
service/account must be selected and provisioned; no scheduler is configured by
`vercel.json`. An every-minute Cloud Scheduler HTTP job is one option.

The first authorized worker execution writes its own `paymentOperations/worker`
heartbeat. Production initiation requires it to be less than five minutes old
and bound to the current mode/key ID. A 2xx webhook acknowledgement only proves
durable receipt, not capture or subsequent processing. Check worker results and
safe diagnostics for deferred events or manual review. Never set a ready flag or
heartbeat manually to bypass this gate.

## First TEST transaction and acceptance matrix

1. Complete the variables, configured deployment, TEST webhook and scheduler.
   Privately verify Razorpay automatic capture is enabled; authorization alone is
   not payment success. Check the actual methods available in the TEST account.
2. Verify the published Firestore rules match the reviewed local protections:
   browser writes to orders/payment internals are denied; administrator actions
   still require both `admin:true` and enabled `adminAccess/{uid}`.
3. Choose an explicitly approved Firebase test account and existing, owner-approved
   test stock/coupon/points data. **Razorpay TEST does not isolate Firestore**:
   this deployment still reserves inventory and writes orders in the configured
   production project. Do not test using real sellable stock or customer balances.
   A separate Firebase test project is not a drop-in environment switch because
   the server currently pins the project; separate isolation requires a reviewed
   deployment plan. This audit creates no test customers or inventory.
4. Sign in as an allowlisted test customer on `https://www.parinayasarees.com`.
   Add the approved test item to Bag, select delivery address, review the current
   INR total, optionally apply a test coupon/points, and continue to Payment.
   Online payment must be labelled TEST and available only to approved accounts.
5. Open Razorpay Checkout once. Select Card and use an official current
   [Razorpay test card](https://razorpay.com/docs/payments/payments/test-card-details),
   for example Visa `4100 2800 0000 1007`, random CVV and a future expiry date.
   Follow its mock-bank success/OTP flow. Use no real card or banking credentials.
6. Confirm the matching Razorpay TEST order is paid and payment captured for the
   exact INR amount. Confirm server-verified customer/Admin status, one internal
   order, one inventory reservation/settlement, correct coupon/points usage and
   selective Bag cleanup. Do not infer success from the modal callback alone.
7. In Dashboard inspect deliveries of the subscribed webhook events: this endpoint
   returns 202 only after signature verification and durable event acceptance.
   Confirm the worker processes the matching event; a sample unrelated provider
   order can acknowledge safely yet remain unmapped, so use the app-created order.
8. Repeat controlled failure, dismissal, callback/network loss, refresh/resume and
   duplicate-delivery scenarios. Check payment status before another attempt;
   unresolved or authorized payments retain their hold. Verify no duplicate charge,
   order, stock deduction or coupon/points use. Verify COD on separate approved
   test inventory once the online lock is resolved.
9. Exercise partial/full TEST refunds from Razorpay Dashboard. Confirm pending,
   failed and processed states are distinct. This app tracks provider refunds but
   does not initiate refunds, automatically restock, or automatically allocate
   loyalty refunds. Loyalty-related refunds deliberately hold spending pending
   an approved accounting allocation workflow; do not clear flags manually.

Use the current official Standard Checkout and test-method documentation for UPI
and net-banking scenarios supported by the account/device. No actual Razorpay
TEST transaction or real webhook delivery is claimed by local mocked checks.

LIVE activation is a separate approval and must remain disabled throughout.
